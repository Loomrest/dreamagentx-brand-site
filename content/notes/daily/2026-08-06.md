## 只贴报错，为什么总收到「重启试试」

周三晚上十点，小李刚把本地服务跑起来，终端突然刷出一屏红字：`TypeError: Cannot read properties of undefined (reading 'map')`。他复制最后一行丢给对话助手，等了半分钟，对面回：「检查变量是否为空、更新依赖、重启服务。」三条都对，没一条能下手。

这种回复不是助手「笨」，是信息不够。报错最后一行往往只告诉你「哪里炸了」，不告诉你「为什么在这一行炸」。DreamAgentX™ 上手实操里，我们把这类提问叫「裸奔式贴错」—— 像只给医生看一张化验单上的箭头，不给年龄、病史、最近吃过什么药。

你真正需要的，是一次对话里把上下文补全，而不是来回追问五轮，每轮再贴一段新日志。下面这套做法，当天就能用。


## 三件套：堆栈、相关代码、你已经排除了什么

把报错交给 AI，至少带上这三块。

**第一，完整堆栈，不要只截最后一行。** 从 `Error:` 或 `Traceback` 开头，到最后一行，原样粘贴。Node 项目里，最后一行可能是 `at Array.map`，真正出问题的往往在往上三行的业务文件路径。Python 同理，`File "app/routes/user.py", line 42` 比 `KeyError: 'email'` 值钱得多。如果你用了框架，把触发报错的那次请求的 URL、方法也写上。

**第二，相关代码，控制在十到三十行。** 不需要整个仓库，把堆栈指向的函数及其调用处贴出来就够。如果涉及配置文件，把对应字段那段也贴上。代码块用 markdown 包起来，标明语言，方便助手对齐行号。贴代码时加一行注释写文件路径，例如 `# src/pages/UserList.jsx`，比只说「在用户列表组件里」精确十倍。

**第三，排除清单 —— 这是大多数人会漏的。** 写清楚你已经试过什么、结果如何。例如：「已确认 `users` 不是 null，是空数组；已打印 `res.data`，接口返回 `{ list: undefined }`；npm 依赖没动过，问题在改完分页逻辑后出现。」这能直接砍掉助手最爱说的「试试重装 node_modules」。

三件事合在一起，助手才能把猜测空间从「整个项目」缩到「这一两个变量链路」。缺任何一件，它都只能靠经验蒙。

## 可直接复制的提问模板

下面这段可以直接改几个填空就用，建议保存到笔记里：

```
我遇到一个报错，请你按「先定位根因 → 再给修改方案 → 最后说明验证步骤」回答。

【环境】
- 语言/框架：
- 运行方式：（本地 dev / Docker / CI）
- 最近改动：（例如：刚加了分页参数）

【完整报错】
（粘贴从 Error/Traceback 到最后一行的全部内容）

【相关代码】
（粘贴 10–30 行，含文件路径注释）

【我已排除】
1. ……（试过什么，结果如何）
2. ……

【请你回答】
1. 最可能的根因是什么？依据堆栈哪一行？
2. 给出最小改动的修复代码
3. 我该怎么验证修好了（一条命令或一个操作）
```

注意模板里加了「依据堆栈哪一行」—— 这会逼助手展示推理过程，而不是甩一句「可能是异步时序问题」就结束。

如果报错出现在浏览器控制台，把 Network 里对应请求的 status 和 response 摘要也写上；如果是 CI 失败，贴上 job 名称和失败步骤编号。环境信息少写一句，就多一轮无效来回。


## 怎么判断它是在分析，还是在瞎猜

收到回复后，花一分钟做质检，比盲目改代码省时间。

**看有没有指向具体行号。** 合格回答会说：「`userList` 在第 28 行 `.map()` 时，上游接口返回的 `list` 字段缺失，导致 undefined。」不合格回答则是：「建议检查 API 返回格式和数据处理逻辑。」后者听着专业，但无法验证。

**让它解释为什么排除其他可能。** 你可以追问一句：「如果原因是 X，堆栈里应该出现什么现象？为什么不是 Y？」靠谱的助手能对照你的排除清单，说明为什么不是依赖损坏、不是版本冲突。如果每次追问都换一个新猜测，且与堆栈对不上，就停止执行，回去补材料重问。

**要求给出可执行的验证步骤。** 好的方案会附带：「改完后刷新 `/api/users?page=1`，response 里应有 `list` 数组；控制台不应再出现该 TypeError。」没有验证步骤的修复建议，先标为「待确认」，不要直接合进 main 分支。

最后说一个新手常犯的错：把助手的回复整段复制进 Issue 或群里问「这样改对不对」，而不附上原始三件套。别人没法帮你看，因为上下文还在你和助手的对话里。养成习惯 —— 每次提问都按模板归档成一条笔记，下次同类报错可以直接复用排除清单。

**今天的行动：** 找一条你最近没解决的报错，按上面的模板重新问一次，把「完整堆栈 + 相关代码 + 排除清单」补全后再发。

明天我们会聊「助手给了修复方案，怎么在小范围里安全试改再合代码」—— 今天先把提问这一环练稳，后面改代码才不至于盲人摸象。
